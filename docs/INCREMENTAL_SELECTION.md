# Incremental selection membership (native profile 1)

This first implementation supports an explicitly enrolled durable view whose expression is a single Query followed by Filter layers, over an ordinary proof-free snapshot. `enroll_incremental_view(id, host)` opts an existing principal-owned view into a private cache; ordinary registration and public graph plans are unchanged. `refresh_view` maintains eligible memberships, and `refresh_view_with_work` additionally returns trusted embedding diagnostics. Those counters are never added to QueryResult, public deltas or adapter messages. [Bounded explicit scheduling](VIEW_SCHEDULING.md) is implemented as a separate native layer.

Eligibility is checked on verified raw input. Legacy and explicit assertions are supported, with schemas, static readers, source order, isolated-node behavior, half-open intervals and all fixed query/filter times preserved. Attachments, external references/proofs, context qualifiers/carriers, generic influence and protected namespaces fall back to the ordinary evaluator. Existing current-result and prior-transition authorization checks remain mandatory. Enrollment grants no authority; each fast read passes the common protected-source guard and applies current primitive readers anew.

The cache holds record fingerprints, membership bits, interval boundaries and endpoint counts. Source/node/structure corrections change the relevant claim fingerprints; tick changes revisit crossed boundaries. Changed source order is rendered in the new source order. Every output is rematerialized with exact current revision pins, including unchanged claims and provenance-only generations. Cold state, missing/corrupt state, evaluator changes and schema/profile changes run full recomputation before seeding. An oracle disagreement returns the authoritative full result, discards the cache and increments a local diagnostic; it never hides a successful ordinary evaluation. Unsupported or over-budget kernels fall back within the same operation snapshot/read budget.

State is bounded before SQLite returns its text and verified by a separately stored SHA-256 digest, strict decoding, evaluator/definition/principal/schema binding and redundant endpoint/boundary indexes. This detects accidental/tampered individual cache fields, including valid JSON bit/count changes. It does not protect against a trusted database administrator consistently rewriting every cache integrity anchor, just as primary storage does not claim that protection. Cached bits never authorize a hidden primitive record. Unsupported/erroring recomputation rolls back tentative state and generation together.

SQLite marker 13 adds private selection and scheduling tables in the existing atomic migration. Older marker12 binaries refuse the store; existing immutable primary rows are unchanged. Limits are 256 enrolled views per principal, 64 MiB serialized auxiliary state per view and 256 MiB total state per principal. A conservative record/index precharge can choose fallback sooner. Existing result/read budgets still apply, and retries cannot reset the shared read budget inside an operation.

The optimization is incremental **membership evaluation**. Loading and integrity-verifying a snapshot remains O(input), as do fingerprint comparison, rebuilding boundary/endpoint indexes from reused decisions, and canonical pre-selection materialization. Final serialization/repinning remains O(output). Fresh permission validation may dominate total work. `source_records` counts raw records supplied to the kernel (additional oracle/authorization loads are not included), `hashed_records` counts visible records fingerprinted by the kernel, and other counters distinguish membership evaluations, crossed candidates, output repinning and fallbacks. They are operation-local logical counts, not timing, allocation or RSS measurements. No speedup or delta-only I/O claim is made.

Tests in `incremental_views.rs` cover one-of-40 correction work, crossed boundaries/restart, explicit negative assertions/readers/order/deletion, valid-JSON corruption and fallback, and marker migration. Independent `root_incremental_views.rs` compares complete results, generations and transitions for fixed-time conjunctions, no-op Filter layers and repeated reader/order changes. `check_selection_migration.py` uses the retained marker12 binary and the feature-only schema observer to check actual process death before migration commit and old-binary refusal. The reviewed [full profile](proposals/INCREMENTAL_VIEWS_PROFILE_1.md) also specifies the implemented bounded scheduler. General E07 remains open.

Local checkpoint validation: 324 workspace test/doctest checks passed with all features; strict all-target/all-feature Clippy and formatting passed. The final small counter/index-validation edits were rechecked by the six focused kernel/oracle tests and lint. Marker12→13 actual process-death/restart/refusal/idempotence passed using the preserved schema12 binary, without rebuilding an old tree. These are local results; hosted CI and independent freeze review are separate.

A small [recorded debug benchmark](benchmarks/selection-local.json) compares five alternating-order refreshes after one corrected claim among 256. It re-evaluates one membership, fingerprints 258 visible records, renders 256 claims and repins two nodes each time. Median incremental end-to-end refresh was **38.24 ms**, versus **28.95 ms** for full recomputation in this local in-memory SQLite fixture. This first implementation is slower overall on that workload; cache/index work and full snapshot/output costs outweigh the saved predicate evaluations. `selection_benchmark` reproduces the fixture; these five debug samples establish no SLO or capacity claim.
