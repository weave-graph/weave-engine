# Signed capability admission foundation

`crates/weave-policy` is a portable verifier. It is not yet wired into engine reads, metadata traversal, adapter installation, capsule receipt, or graph mutation. The existing `HostContext` remains a trusted local embedding API. This milestone does not make it a remote authentication boundary or close E04/E09.

A host installs scoped root authorities, an audience, current policy revisions, a policy epoch, a trusted clock and revocation state out of band. Neither a graph, a signed token nor an executable plan can install these values. Actions are distinct: discover, read, traverse, propose, publish and delegate. Scope is an exact graph/branch pair; there are no wildcard expansions. All action and time constraints are checked again at admission.

A capability binds its issuer and subject Ed25519 keys, audience, policy revision, exact scopes, half-open validity interval, remaining delegation depth and parent token identity. Descendants require the parent's delegate action for every delegated scope. They can only reduce scope, lifetime and delegation depth. Every signature is verified strictly; keys, tokens and intermediate delegation links can be revoked by the current host state. Removing or replacing a root policy invalidates admission under the old policy. Offline hosts only know their supplied revocation state; disconnected global revocation is not promised.

The leaf subject must sign a request binding the exact capability ID, audience, operation, body digest, nonce and short validity interval. The host passes the independently decoded expected operation to `verify_request`. A valid read proof cannot authorize a publish operation or different request body. Multi-operation plans require checks for every operation and all transitive reads/traversals; checking only an outer label is insufficient.

`VerifiedRequest` is a candidate admission with private fields. Its replay identity binds subject, audience and nonce independently of body or chain. Verification rejects nonces already present in host-provided state. **Verification alone does not reserve the nonce.** The integration layer must call `check_boundary` inside its storage transaction, then atomically reserve that identity and apply the authorized operation or durable receipt. The boundary check rechecks body/operation binding, audience, current policy epoch, half-open request time and consumed nonce state. Every trust, policy or revocation change must advance that host epoch. This prevents retaining a candidate past its expiry or substituting another body at execution. Concurrent admission, crash recovery, authorization-aware caches and event delivery remain runtime integration work. Do not construct an unrestricted `HostContext` from a verified read proof.

## Encoding and budgets

The experimental wire is typed JSON with unknown fields rejected. Signatures are over UTF-8 compact `serde_json` serialization of a domain string and a fixed-order typed body as a two-element array. Sets are sorted; graph/branch scopes must be strictly ordered and unique. Public keys and signatures use lowercase hexadecimal. Domain strings separate capability signatures, request signatures, token identities and nonce identities. Body digests bind exact caller-supplied bytes. This is a specified local profile, not a claim of RFC 8785 canonical JSON or UCAN interoperability. Future encoding changes require a new version.

Proofs are bounded to 64 KiB and eight tokens; each token has at most 64 scopes and bounded identifiers. Request validity is at most five minutes and never extends beyond its capability. Time values are host-supplied integer milliseconds, with no hidden wall-clock read. No key generation, deployment key storage, network transport or bearer-token logging is performed by the verifier. Signing helpers accept host-owned keys; fixed seeds occur only in public tests.

## Evidence and remaining work

Adversarial tests cover strict signature tampering, self-installed authority, unsupported actions, foreign graph scopes, widened expiry/delegation, wrong parent, missing delegation authority, intermediate token/key revocation, policy replacement, audience mismatch, half-open expiration, signed body/operation/nonce substitution, consumed nonces, weak keys, unknown fields and input budgets. Native tests and a WASM compile check establish a portable verifier, not browser/mobile runtime acceptance. This code needs further independent review and runtime enforcement before use as a production trust boundary.

Cryptographic operations use the upstream [ed25519-dalek 3 documentation](https://docs.rs/ed25519-dalek/3.0.0/ed25519_dalek/) and its [strict verification API](https://docs.rs/ed25519-dalek/3.0.0/ed25519_dalek/struct.VerifyingKey.html#method.verify_strict). Weave defines the application authorization profile; it does not implement its own signature primitive.
