# Bounded durable living-view scheduling

The native host explicitly enables and drives scheduling. This API grants no read, publish or remote installation authority, and adds no protocol operator:

1. Register the view and call `enroll_incremental_view(id, host)` for its principal-owned cache.
2. Call `enable_view_schedule(id, host)`. Enrollment and an initial pending refresh commit together with cursor initialization. Repeating enrollment preserves a newer requested tick and does not add another job.
3. Call `scan_view_work(host, ViewScanBudget { max_events, max_views })` to page graph events into pending work. Limits are 1,024 completed events and 256 view notifications per call; zero budgets do no scan work.
4. Use `request_view_tick(id, instant, host)` to request explicit data time. Requests coalesce to the latest nondecreasing tick; this instant is never authority time.
5. Call `drain_view_work(host)` to publish at most one oldest pending view. It returns a small trusted-host outcome, not the graph or an authorization token. Read graph values and transitions through the ordinary guarded view APIs.

One pending row per enrolled view bounds coalescing; at most 256 views are enrolled per principal. The private event cursor records the current event and the last dependency ID scheduled within it. Queue insertion and cursor advancement are one SQL transaction, so an interrupted fan-out resumes without skipping later views. Owners with the same view ID have independent queues/cursors. Pinned sources have no live-head subscription. Initial enrollment queues a fresh evaluation from actual heads, closing the race with events already traversed by the owner cursor. Source events are notifications; their payloads never replace verified query input.

One successful drain is one writer transaction and one installed-clock sample. It reads the newest heads and coalesced tick, performs incremental selection or exact fallback, then atomically commits result, generation, current/prior transition guards, selection state, processed input manifest and pending acknowledgement. The manifest contains exact input snapshot pairs, observed live graph/branch heads, definition/evaluator/schema fingerprints, tick, generation and completeness. Internal event offsets are not freshness or permission certificates. Partial output remains explicitly noncurrent. No source graph event is fabricated for scheduling or expiry.

Source changes and ticks between published states coalesce; intermediate states are not promised as deliveries. Existing exact retractions and one-transition retention remain unchanged. A synchronous refresh can move ahead of queued time; the drain uses the maximum of requested and committed ticks, so stale work cannot poison the queue. A newer queued tick makes the old snapshot noncurrent even when the caller supplies the old tick. `AllowStale` still revalidates current authority; `RequireCurrent` rejects stale heads/ticks/partial coverage.

Failure rolls back computation, leaving the request and its prior manifest unacknowledged. A separate bounded SQL/clock operation records a capped error code/attempt count and moves that still-pending job behind other pending jobs. This avoids a permanently failing oldest view starving healthy work. It does not claim that the erroring view eventually succeeds. Failure of the rotation itself, including database contention or unavailable authority clock, is explicit and cannot be turned into an acknowledgement. Repeated host calls retry; there is no background thread, timer, unbounded loop or compute-outside-transaction lease.

Quotas cover 64 MiB selection state per view, 4 MiB processed manifest per view, and a combined 256 MiB auxiliary byte budget per principal. SQL returns bounded identifiers/pages before Rust collection; state/manifest output is charged before accumulation. Definition/result and shared operation limits still apply. An in-quota workload may exhaust the shared read budget and remain pending. Progress under arbitrary fan-out, sustained contention, missing dependencies or policy failure is not guaranteed. No retention/GC or universal policy/quarantine-availability notification is claimed; those changes can still require explicit synchronous refresh.

SQLite marker 13 introduces `view_selection`, `view_schedules` and `view_schedule_cursors` together. The kernel-only marker13 checkpoint was never public; marker12 is the supported public predecessor. `check_selection_migration.py` verifies all three tables absent after a precommit process death, all present after restart, and actual marker12-binary refusal. The current native C ABI and shared graph protocol are unchanged.

`view_schedule.rs` tests coalesced correction/deletion/ticks, exact full-result parity, generation behavior, current governance expiry without head movement, fair error rotation across restart, one-clock success, two writers, pinned sources and no fake source events. Independent `root_view_schedule.rs` tests restart after every fan-out page, principal isolation and unwind-safe queue/publication observers. The feature-only `view_schedule_probe` plus `check_view_schedule_recovery.py` kill actual processes before and after scan/publication commits and check queue/cursor, manifest/result/transition and lost-response retries. These hooks are not production callbacks.

The [incremental selection kernel](INCREMENTAL_SELECTION.md) reduces predicate membership work for its supported subset. General joins/rules/context/metadata maintenance, fine-grained source storage, richer priorities/retention, remote installation and push delivery remain open E07 work.
